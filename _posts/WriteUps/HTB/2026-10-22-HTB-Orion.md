## What is Craft CMS?

Craft CMS is a flexible PHP-based content management system built on the **Yii 2** framework. It is used by enterprises, government agencies, and high-traffic digital platforms. Because it runs on PHP/Yii and exposes a web-facing action routing system, any critical vulnerability in its request handling pipeline is internet-exploitable with no authentication required — making CVEs against it particularly high-severity.

In April 2025, researchers at Orange Cyberdefense discovered **CVE-2025-32432**, a CVSS 10.0 remote code execution vulnerability affecting all Craft CMS versions from 3.x through 5.x. It was chained in the wild with **CVE-2024-58136**, a flaw in the underlying Yii framework itself. Together, these two CVEs allowed unauthenticated attackers to fully compromise servers — and approximately 300 real-world deployments were confirmed compromised before patches were widely applied.

## Exploitation

### CVE-2025-32432 — Craft CMS Unauthenticated RCE

**CVE-2025-32432** is a CVSS 10.0 unauthenticated remote code execution vulnerability affecting Craft CMS versions 3.x, 4.x, and 5.x. It was discovered in April 2025 by researchers at Orange Cyberdefense during a forensic investigation of a compromised server, and was patched in versions 3.9.15, 4.14.15, and 5.6.17.

The vulnerability lives in Craft's **image transformation** feature. Craft allows administrators to define transforms — operations like resizing or reformatting images — that are applied on the fly when an asset is requested. The flaw is that an unauthenticated attacker can send a crafted POST request to the image transform action endpoint, and **the data within that POST is interpreted by the server** rather than safely sanitised. This leads to PHP code execution in the context of the web server process.

The exploit requires one prerequisite: **a valid asset ID** from the target installation. Craft tracks uploaded files as "assets" with numeric IDs stored in its database. The transform endpoint only processes requests tied to existing asset IDs — but because the ID enumeration itself is unauthenticated, this is a trivially bypassed gate.

This CVE is a spiritual successor to **CVE-2023-41892**, an earlier unauthenticated RCE in Craft 4, and the two share code-path DNA. CVE-2025-32432 is formally described as "an additional fix" for the 2023 vulnerability.

It is chained here with **CVE-2024-58136** (CVSS 9.0), a flaw in the underlying Yii 2 framework's routing and parameter handling that facilitates the initial request manipulation.

### Initial Foothold

A public proof-of-concept for CVE-2025-32432 is available at [github.com/cd-ratel/CVE-2025-32432](https://github.com/cd-ratel/CVE-2025-32432). It is a Python script that automates the full exploit chain. Dependencies were already satisfied in the HTB Pwnbox environment.

```bash
git clone https://github.com/cd-ratel/CVE-2025-32432
cd CVE-2025-32432
pip install -r requirements.txt
```

#### How the Exploit Chain Works

Before running the script it is worth understanding what it does under the hood — this is what separates a script kiddie from someone who actually knows what they exploited.

The PoC executes a **three-stage attack chain:**

**Stage 1 — CSRF Token Acquisition.** Craft CMS requires a valid CSRF token for all action endpoint requests. The script fetches one unauthenticated from `/actions/users/session-info`. This endpoint is intentionally public — it is how Craft bootstraps frontend sessions — but the script abuses it to obtain a token that legitimises the subsequent exploit requests.

**Stage 2 — Asset ID Probing.** The image transform endpoint only accepts requests referencing a valid, existing asset ID. The script probes sequentially starting from ID 1. A `500 Internal Server Error` response (as opposed to a clean `404`) signals that the asset exists and Craft attempted to process it — the 500 occurs because the malicious `itemFile` parameter causes an error inside the transform pipeline, not because the asset was absent. **Asset ID 2** returned HTTP 500, confirming it as a valid target.

**Stage 3 — Log Poisoning via User-Agent.** With a valid asset ID in hand, the script poisons the nginx access log at `/var/log/nginx/access.log`. It sends an HTTP request with a PHP webshell embedded in the `User-Agent` header:

```
User-Agent: <?php system($_GET['cmd']); ?>
```

Every request to the nginx server is appended to this log file verbatim, including the raw User-Agent string. The exploit then triggers the Craft transform gadget with `itemFile=/var/log/nginx/access.log` — instructing PHP to **include and evaluate** the log file as PHP code. The embedded webshell executes, and the script passes commands through the `cmd` GET parameter.

The exploit confirmed asset ID 2 is valid (HTTP 500 on the transform endpoint indicates Craft attempted processing, rather than a clean 404 meaning asset not found). However, the log poisoning stage failed.

This is a shared-lab artefact common in HTB environments: because the nginx access log is written to by every player attacking the same machine instance, a previous player's `<?php ... exit; ?>` block was already present in the log. Since PHP evaluates the log file top-to-bottom and the older block runs first, it exits before the new payload can fire. Even after a machine reset, the log fills up again almost immediately on a popular machine.

The Python PoC's log poisoning technique is fundamentally unreliable in this environment. A different exploitation method was needed.

#### Why the Metasploit Module Succeeded

The critical difference is visible in the module's check output: `Leaked session.save_path: /var/lib/php/sessions`. Instead of poisoning the shared nginx access log, the Metasploit module:

1. **Leaks the PHP session directory** by triggering a verbose Craft error that discloses the `session.save_path` configuration value — another consequence of `devMode` being enabled.
2. **Poisons a PHP session file** at `/var/lib/php/sessions/sess_<id>` by injecting PHP code into a session variable that Craft writes to disk.
3. **Triggers evaluation** of that session file through the transform gadget using `itemFile=/var/lib/php/sessions/sess_<id>`.

Unlike the access log — which is shared, append-only, and polluted by every other player — each player's PHP session file is unique to their session ID. There is no cross-contamination between players, and no stale `exit` blocks from prior runs. This makes session poisoning a significantly more robust technique for this CVE in shared lab environments.

The module's `excellent` rank and built-in `AutoCheck` reflect the reliability of this approach.

### Credential Discovery — The .env File

> **🧠 Think First!**
> You have a shell as `www-data` inside a Craft CMS application. Where would the application store its database credentials? Think about how PHP applications typically handle environment-specific configuration before reading on.

Craft CMS follows the [Twelve-Factor App](https://12factor.net/) convention of storing all environment-specific secrets in a `.env` file in the project root — one directory above the public webroot. This file is never served publicly by nginx (the webroot is `/craft/web/`, not `/craft/`), but it is fully readable by the web server process.


This single file yields several critical findings:

| Variable | Value | Significance |

| `CRAFT_SECURITY_KEY` | `RRS86F6i2JQKdC6kfEI7frVxA47WVMx8` | Craft's encryption key for signed URLs and sensitive data |

Running the application as the MySQL `root` user means that a SQL injection vulnerability anywhere in Craft would give an attacker full database server control — `FILE` privileges, `INTO OUTFILE`, and the ability to read arbitrary files from the database server process.

### Hash Cracking

The bcrypt hash was saved and attacked with Hashcat using the rockyou.txt wordlist.

```bash
echo '$2y$13$e9zuohgFZzGtbQalcn9Mz.5PJbjxobO0GMbXo8NHp3P/B42LUg0lS' > hash.txt
hashcat -m 3200 hash.txt /usr/share/wordlists/rockyou.txt
```

**Hashcat mode 3200** is bcrypt/Blowfish. Running on CPU only (AMD EPYC via OpenCL) the cracking speed was approximately **10 H/s** — deliberately slow by design, as bcrypt's cost factor is intended to make brute-forcing impractical. Despite this, the hash fell in **65 seconds** with only 656 candidates tested — it was near the very top of rockyou.txt.

> **🧠 Think First!**
> You have discovered a Telnet service running on localhost port 23. Before connecting, think: what information do you need to exploit this? What would you check first — the version or the credentials? What is unusual about a Telnet service running internally on a modern Ubuntu server?

Telnet is a decades-old plaintext remote access protocol that was superseded by SSH in most environments. Seeing it running internally on a modern Ubuntu 22.04 server in a CTF context is a strong signal that it is intentionally vulnerable — the question is which CVE targets it.

### CVE-2026-24061 — inetutils-telnetd Authentication Bypass

A search for `inetutils-telnetd 2.7 exploit` reveals **CVE-2026-24061**, an authentication bypass vulnerability affecting inetutils-telnetd versions 1.9.3 through 2.7.

#### How the Vulnerability Works

The TELNET protocol supports a negotiation option called **NEW-ENVIRON**, which allows the connecting client to send environment variables to the server before authentication occurs. The `inetutils-telnetd` daemon passes these environment variables directly into the login process that handles authentication.

The Linux `login` binary accepts a `-f` flag meaning "already authenticated — do not prompt for a password." By sending the environment variable `USER='-f root'` via the NEW-ENVIRON option, the client tricks `telnetd` into invoking `login` with the arguments `-f root`, which bypasses the password prompt entirely and logs in as `root`.

This is a pre-authentication vulnerability — no valid credentials are required at any point. The entire authentication mechanism is bypassed by abusing the TELNET protocol's own option negotiation.

## Defense and Mitigation

**Patch immediately.** Any Craft CMS installation running a version below 3.9.15, 4.14.15, or 5.6.17 is directly exploitable by an unauthenticated attacker with network access. The patch is one `composer update` away.

**Disable devMode in production.** The `devMode` setting in `config/general.php` is intended for local development only. When enabled on an internet-facing server, it dumps full stack traces, framework versions, server file paths, and internal application state into HTTP responses. Any of this information assists an attacker in targeting the correct CVE and navigating the server post-exploitation. The correct configuration is:

```php
// config/general.php
return [
    'devMode' => false,   // Never true in production
];
```

**Restrict the admin panel.** The Craft admin panel at `/admin/login` should never be accessible from the public internet. Restrict access to trusted IP ranges via nginx configuration:

```nginx
location /admin {
    allow 10.0.0.0/8;     # internal range only
    deny all;
}
```

**Apply Web Application Firewall rules.** The transform endpoint that CVE-2025-32432 targets has a known request signature. WAF rules blocking unexpected POST bodies to `/actions/assets/generate-transform` or similar routes provide a stop-gap while patching is arranged.

**Upgrade Yii.** CVE-2024-58136 exists in the Yii 2 framework layer. Upgrade to Yii 2.0.52 or later alongside the Craft CMS patch.

## Key Takeaways

- **Technology disclosure is a real risk.** A single line in the page footer (`Powered by CraftCMS`) handed us a precise CVE target. Suppress or remove CMS fingerprinting from production sites.
- **devMode is a loaded gun.** Enabling `devMode=true` on a public server is a critical misconfiguration. It disclosed the framework version, server file paths, and application internals in a single HTTP response — all of which fed directly into the attack chain.
- **Unauthenticated RCE on a CVSS 10 CVE means patch speed matters.** CVE-2025-32432 was being exploited in the wild before many organisations had applied the patch. The lesson is that high-severity CMS vulnerabilities move from disclosure to exploitation in days.
- **When one exploit technique fails, understand why before switching tools.** The Python PoC's log poisoning failed due to shared-lab pollution, not a fundamental flaw in the CVE. Understanding the mechanism pointed directly to session poisoning as a more reliable alternative — and to the Metasploit module that implemented it.
- **Config files are treasure maps.** The `.env` file disclosed database credentials, the encryption key, environment configuration, and confirmed `devMode=true`. Protecting application config files from the web server process should be a baseline hardening requirement.
- **Bcrypt slows attackers but cannot save weak passwords.** A cost-13 bcrypt hash cracked in 65 seconds because the underlying password (`darkangel`) was common. Strong hashing algorithms only buy time — the password itself must also be strong and unique.
- **Internal services are part of the attack surface.** Port 23 was invisible from outside but fully exploitable from inside. Enumerate localhost ports as a standard post-exploitation step — `ss -tlnp` takes two seconds and can reveal the entire privilege escalation path.
- **Legacy protocols carry legacy vulnerabilities.** Telnet was deprecated for SSH decades ago. Running `inetutils-telnetd` on a modern server introduced CVE-2026-24061 — a trivial authentication bypass that handed root access in a single exploit run. Avoid legacy network services entirely in production environments.
